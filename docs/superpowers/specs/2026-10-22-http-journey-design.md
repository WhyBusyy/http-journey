# http-journey 설계 문서

- 작성일: 2026-10-22
- 상태: 승인됨 (2026-10-22)
- 위치: `~/http-journey` (신규 독립 레포, Vercel 단독 배포)

## 1. 무엇이고 왜 만드나

주니어 개발자가 **HTTP 요청 하나가 실제로 어떤 길을 거치는지**를 물리적·논리적으로 한 번에 이해하게 해 주는 한국어 인터랙티브 웹페이지.

- 특정 장애 해결용이 아니라 "알아두면 두고두고 유용한" 교양 콘텐츠다. 읽고 나서 "아, 그래서 그렇구나"가 남으면 성공이다.
- 영어 자료가 부담스러운 사람을 위해 **설명은 한국어**, **technical term은 영어 그대로**(DNS, TCP handshake, TLS, event loop, libuv, connection pool 등) 쓴다. 용어마다 한국어 한 줄 설명 툴팁을 붙인다.
- 서버 쪽은 **Node.js 기준**이다.

### 영감과 독창성 (중요 제약)

- The Nodebook의 200ms 시각화(https://200ms.thenodebook.com)에서 **아이디어(요청 하나를 시간순으로 따라가는 형식)만** 영감을 받았다. 해당 콘텐츠는 라이선스가 없고 약관상 재사용에 허락이 필요하다.
- 따라서 원본의 **문장, 섹션 구성·소제목, 예시 시나리오, 비유, 시각 디자인, 연출, 코드는 일절 가져오지 않는다.** 원본을 옆에 두고 쓰지 않는다. 사실 확인은 RFC, MDN, Node.js 공식 문서, AWS 문서 등 1차 자료로 한다.
- 페이지 하단에 "The Nodebook의 200ms 시각화에서 아이디어를 얻었습니다" + 링크를 남긴다.

### 원본 대비 차별점 (우리가 채우는 빈칸)

1. **두 레인 구조**: 매 단계에서 논리(프로토콜·소프트웨어)와 물리(하드웨어·매체)를 한 다이어그램 안에 나란히 보여준다.
2. **실무 연결**: 단계마다 "실무에서는" 박스. DevTools Network 탭의 해당 칸, 흔한 에러(`ENOTFOUND`, `ECONNREFUSED`, `ETIMEDOUT`, 502/504), keep-alive·connection pool로 시간이 줄어드는 이유 등.
3. **주니어 눈높이**: 하드웨어는 다루되 기본은 2~3줄, 깊은 내용은 "더 깊이 보기"로 접는다.
4. **한국 사용자 시나리오** (아래 3절).

## 2. 목표 / 비목표 / 안티목표

**목표**
- 끝까지 스크롤하면 요청 하나의 전체 경로(탭 → 응답이 화면에 그려짐)를 물리·논리 양쪽으로 설명할 수 있게 된다.
- 단계별 소요 시간 감각(어디가 느릴 수 있는지)을 숫자로 체감한다.
- 각 단계를 실무 증상(에러, DevTools)과 연결한다.

**비목표**
- 원본 수준의 바이트 단위 심층 분석(패킷 헤더 필드 전부, 광케이블 중계 구간 등).
- 다국어 지원(한국어만).
- 사용자 계정, 댓글, 분석 대시보드 등 부가 기능.
- 실시간 측정 기능(사용자 브라우저에서 직접 요청을 날려 재는 것).

**안티목표 (기술적으로 돌아가도 실패로 보는 것)**
- 원본을 번역·각색한 것처럼 보이는 결과물.
- 용어 나열식 교과서가 되어 주니어가 중간에 이탈하는 것.
- 애니메이션이 무겁거나 모바일에서 버벅여서 "요청이 빠르다"는 이야기를 하는 페이지가 느린 것.
- 틀린 기술 사실(특히 숫자). 숫자는 근거가 있어야 한다.

## 3. 시나리오

서울의 한 사용자가 **폰(5G/LTE)**으로 쇼핑 앱(웹)의 **"주문하기"** 버튼을 탭한다. 요청 `POST /api/orders`는 **AWS 서울 리전(ap-northeast-2)**의 Load balancer → Node.js 서버 → 같은 리전의 Postgres를 거쳐 응답이 돌아오고, 화면에 "주문 완료"가 그려진다. 총 약 200ms 규모.

- 첫 요청이라 DNS·TCP·TLS를 모두 거치는 cold 경로를 보여주고, "실무에서는"에서 재사용(keep-alive, DNS cache) 시 생략되는 시간을 짚는다.

### 프로토콜·인프라 가정 (빌더 판단으로 확정)

- **HTTP/2 over TCP**, **TLS 1.3**(1-RTT). HTTP/3(QUIC)는 TCP 단계를 없앤다는 점만 3·4단계 "더 깊이 보기"에서 언급.
- API 요청이므로 **CloudFront 없음**. 클라이언트 → **ALB**(여기서 TLS 종료) → 같은 VPC의 Node.js(EC2 또는 ECS, 평문 HTTP) → **RDS Postgres**(같은 리전, 다른 서버).
- Node 서버는 Postgres와의 연결을 connection pool로 이미 열어 둔 상태(DB 구간엔 handshake 없음).

## 4. 페이지 구조

단일 페이지, 위에서 아래로 읽는 **스크롤 스토리** + 마지막에 **워터폴 전체 그림**.

1. **Hero**: 제목(가칭 "요청 하나의 200ms", 숫자는 8절 규칙에 따름), 한 줄 소개, 시나리오 한 문단, 스크롤 유도.
2. **상단 고정 진행 바**: 스크롤에 따라 경과 ms가 누적 표시(예: `62ms / ~200ms`).
3. **Step 섹션들** (아래 표). 각 섹션 구성:
   - `Step N · +XXms` 라벨, 쉬운 한국어 제목, 한 줄 요약
   - **두 레인 다이어그램**(5절)
   - 본문 설명 2~4문장, 용어는 파란 칩 + 한국어 툴팁
   - "＋ 더 깊이 보기" 접기 영역 (하드웨어·프로토콜 심화)
   - "실무에서는" 박스
4. **워터폴 전체 그림**: DevTools Network 탭과 비슷한 가로 막대 타임라인. 막대 hover 시 강조, 클릭 시 해당 Step 섹션으로 부드럽게 스크롤.
5. **Footer**: 참고 자료(1차 출처) 목록, 영감 출처 링크, 만든 사람.

### 단계 구성

| # | 단계 | 논리 레인 | 물리 레인 | 실무에서는 |
|---|---|---|---|---|
| 0 | 탭 | 터치 이벤트 → JS `onClick` → `fetch()` | 터치스크린 센서 → OS → 브라우저 | |
| 1 | URL과 캐시 | URL 파싱, HTTP cache 확인 | 기기 내부 (CPU, 메모리) | `Cache-Control` |
| 2 | DNS | DNS query / response | 폰 modem → 기지국 → 통신사 DNS resolver | `ENOTFOUND`, DevTools DNS Lookup |
| 3 | TCP | 3-way handshake (`SYN` / `SYN-ACK` / `ACK`) | 무선 구간 → 통신사 코어망 → 백본 → AWS 리전 | `ECONNREFUSED`, keep-alive |
| 4 | TLS | 인증서 검증, 키 교환 | 같은 경로 왕복 (RTT 체감) | 인증서 오류 |
| 5 | 서버 도착 | Load balancer → Node 프로세스 | 데이터센터 스위치 → 서버 NIC → interrupt → kernel | 502 / 504 |
| 6 | Node 내부 | event loop, libuv, 핸들러 실행 | CPU core, 단일 main thread | blocking 코드의 위험 |
| 7 | DB | connection pool → Postgres 쿼리 | 옆 서버로 가는 네트워크 hop → SSD/EBS | pool 고갈, 느린 쿼리 |
| 8 | 응답과 렌더링 | 응답 → JSON 파싱 → DOM 업데이트 | 같은 길로 귀환 → GPU → 디스플레이 refresh | TTFB |

## 5. 두 레인 다이어그램 (핵심 컴포넌트)

사용자가 시안 비교 후 선택한 방식(B안). 시안: `mockups/layers.html`의 "B. 두 레인 다이어그램" 카드와 하단 워터폴. (`mockups/layout.html`은 초기 레이아웃 비교로, A 스크롤 스토리 + C 워터폴 조합이 채택됨.) 시안은 분위기 참고용이며 문구·숫자는 임시값.

- **레이아웃 (빌더 판단으로 확정):** 다이어그램은 화면에 고정(sticky)하지 않고 **각 Step 섹션 안에서 본문과 함께 흘러간다.** 진행값은 그 섹션이 뷰포트를 지나는 비율로 계산한다. 화면에 고정되는 것은 상단 진행 바뿐이다. 모바일 성능과 구현 단순성 때문.
- 하나의 카드 안에 위 **논리 레인**, 아래 **물리 레인**.
- 논리 레인: 해당 단계의 메시지 칩이 시간순으로 나열되고, 스크롤 진행에 따라 하나씩 활성화(비활성은 흐린 회색).
- 물리 레인: 장비 노드(아이콘 + 라벨)가 선으로 연결되고, 파란 점(패킷)이 스크롤 진행에 맞춰 노드 사이를 이동. 응답 방향일 때는 반대로 이동.
- 두 레인은 **같은 진행값**을 공유해서 "지금 이 메시지가 물리적으로 여기를 지나는 중"이 보인다.
- 모바일에서는 물리 레인 노드를 가로 스크롤 없이 줄바꿈 또는 축약 라벨로 처리.

## 7. 기술 스택 (사용자 결정)

- **Astro** (정적 생성) + **React islands**(인터랙티브 부분만) + **Tailwind CSS** + **motion**(framer-motion 후속 패키지)
- 배포: **Vercel** (정적 출력)
- 선택 이유: 본문은 JS 없는 HTML로 빠르게, 다이어그램·워터폴·툴팁만 hydrate. SEO와 링크 미리보기(OG)가 기본으로 된다.
- 섹션 간 공유 상태(현재 Step, 경과 ms)는 가벼운 공유 store(nanostores 등) 또는 스크롤 위치 직접 계산으로 연결.
- 참고 버전(2026-10-22 기준 최신): astro 7.4.x, @astrojs/react 7.1.x, @astrojs/vercel 11.0.x, motion 14.5.x, nanostores 1.5.x.

## 8. 숫자(ms)의 근거

- 단계별 ms는 "대략 이 정도" 감을 주는 대표값이며, 각 값 옆이나 footer에 근거를 둔다.
- **근거 (사용자 결정):** 공개 측정 자료·공식 문서 + 빌더가 이 맥(유선/Wi-Fi)에서 잰 값(`curl -w`로 AWS 서울 리전 엔드포인트 DNS/TCP/TLS 타이밍, 로컬 Node·Postgres 처리 시간)을 조합한다. 모바일 무선 구간은 공개 자료로 보정한다. 직접 5G 측정은 하지 않는다.
- 이 조합 방식과 측정 환경을 footer(또는 "숫자에 대하여" 메모)에 명시한다.
- 페이지에 "환경에 따라 크게 달라진다"는 안내를 명시한다.
- **(빌더 판단으로 확정)** 모든 ms 값과 출처는 데이터 파일 한 곳에 모은다. 근거가 확보되기 전에는 임시값으로 개발하고, 임시값은 코드에서 표시(예: `provisional: true`)해 출시 전 전부 교체한다.
- **(빌더 판단으로 확정)** 제목·진행 바의 총합은 데이터에서 계산해 표시한다. 측정 합계가 200ms에서 크게 벗어나면 제목 숫자를 실제 합계에 맞춘다(시나리오는 유지). 가칭 "요청 하나의 200ms"는 확정 제목이 아니다.

## 9. 콘텐츠 집필과 검수 (사용자 결정)

- **빌더(Claude)가 모든 본문을 쓴다**: Step별 본문, "더 깊이 보기", "실무에서는", 용어 툴팁, footer 출처 목록.
- 1차 출처(RFC, MDN, Node.js 공식 문서, AWS 문서, PostgreSQL 문서)를 근거로 쓰고, 각 사실 주장에 출처를 연결해 둔다(검수용).
- **사용자가 검수한다.** 계획에 검수 시점을 넣는다: 최소한 (1) 첫 Step 하나를 완성한 시점에 톤·깊이 확인 (2) 전체 초안 완료 후 사실·문장 검토. 검수 전 콘텐츠는 확정으로 취급하지 않는다.
- 1절의 독창성 제약을 집필에도 그대로 적용한다.
